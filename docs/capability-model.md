# 控制能力与验证边界

## 控制对象

一条控制请求至少涉及四个不同对象。不要把它们合并为一个“预设”。

| 对象 | 作用 | 例子 |
| --- | --- | --- |
| 实体灯珠 | 发光硬件。 | `D1` 至 `D23`。 |
| 目标集合 | 本次请求作用的点位。 | 全身，或局部点位索引 `0`。 |
| 显示参数 | 本次请求的颜色、亮度和灯效等字段。 | RGB `FF0000`、亮度字节 `0A`、灯效编号 `0`。 |
| 预设槽位 | 存放设置的编号。 | 局部预设槽位 `0`。 |

当前逐点试色证明本台设备能区分 `D1–D23`。它没有证明 23 颗灯珠能在同一时刻保持 23 组不同的颜色和亮度。

## 能力状态

| 能力 | APK 能否表达 | 本台设备的实测状态 | 下一项证据 |
| --- | --- | --- | --- |
| 读取三类预设列表 | 有 `40`、`30`、`50` 命令。 | 已收到对应通知。 | 有已保存预设时的完整列表响应。 |
| 全身临时试色 | `43` 有 RGB、亮度和灯效等字段。 | 亮度字节 `0A`、灯效编号 `0` 的白光和红光已亮。 | 其他颜色、亮度和灯效的实物表现。 |
| 局部临时试色 | `33` 可传一个或多个点位索引，并附一组 RGB、亮度和灯效。 | 逐个索引 `0–39` 已测试；D1、D2 已在一条 `33` 请求中同时亮红。 | 两条不同局部试色能否并存。 |
| 单颗独立调色 | 可以用 `33` 单独指定某个点位及 RGB。 | D1–D23 已分别亮红；D1 已单独亮绿。亮度 `05` 与 `0A` 目测差异不明显。 | 选第二颗复核绿色；用可控环境验证亮度变化。 |
| 23 颗同时显示不同颜色 | APK 的单条 `33` 请求对所选点位只带一组 RGB 和亮度。高级预设可引用局部预设。 | D1、D2 多点试色已确认同亮红；同一条请求不能为各点携带不同 RGB。 | 明确两条不同局部试色能否并存，或保存多个局部预设后能否组合显示。 |
| 官方动态灯效 | APK 列出 `0–18` 共 19 个灯效编号。 | 编号 `1` 已让 D1 红光重复明暗约 3 次；编号 `3` 的全身试色让全部 23 颗灯珠按装模路线出现。编号 `0` 的试色约 3 秒后熄灭。其余编号未测。 | 补充编号 `3` 的时序细节，再设计其他模式的试验；更长动画的断连后行为仍未知。 |
| 预设保存与切换 | APK 有保存、读取详情和切换命令。 | 未发送保存或切换命令。 | 在明确回退方法和供电状态后，做单槽位测试。 |
| 高级组合与顺序 | APK 可选择局部预设并设置模式、方向、速度等字段。 | 只读取过高级列表。 | 先验证局部预设保存和详情，再测试高级组合。 |

“APK 能表达”只指当前可读的发送代码有相应字段或命令。它不证明固件一定实现该能力。

## 参数属于哪一层

| 参数 | APK 的使用方式 | 限制 |
| --- | --- | --- |
| `colorType` | 全身和局部编辑页中，`0` 表示单色，`1` 表示渐变色。 | 发送报文只有一组 RGB；第二种颜色从何而来未知。 |
| RGB | 全身和局部预设各发送三个颜色字节。 | App 取色时还会按亮度滑块缩放 RGB。任意 RGB 在设备上的显示未验证。 |
| `light` | 全身和局部预设的亮度字节。Android 滑块范围为 `1–100`。 | 滑块范围不是固件的电气或协议上限；本台设备只试过 `0A`。 |
| `effectMode` | 全身和局部预设的灯效编号 `0–18`。 | 名称来自 App。实际动画未知；局部报文没有速度或方向字段。 |
| `lightType` | 全身和高级预设中的方向字段；App 显示正向 `0`、逆向 `1`。 | 哪些灯效使用方向未知。 |
| `speed` | 全身和高级预设中的速度字节；Android 滑块范围为 `1–100`。 | 数值与实际周期的关系未知。 |
| `step` | 高级预设保存命令中的“开启间隔”字段；Android 滑块范围为 `1–10`。 | 单位未知。高级临时预览命令的尾字节固定为 `01`，没有使用当前滑块值。 |

高级预设的 `model` 字段不能直接当成上面的 19 个灯效编号。当前高级编辑页没有找到设置这 19 个编号的调用。高级顺序保存命令 `54` 与高级主预设保存命令 `53` 也是两次不同写入。

## 呼吸灯的两种实现路径

官方 App 把“单色呼吸”列为灯效编号 `1`。单次 `33` 试色已使 D1 红光重复“突然变亮、缓慢变暗”约 3 次，用户感觉略有卡顿；总共约 3 秒后熄灭。App 代码没有按动画帧连续发送 RGB 或亮度，本次 Python 日志只记录一条 TX。因此“动画在设备侧执行”有实机观察支持，但本轮没有采集 BLE 空口数据或固件代码；具体实现仍是推断。脚本在发包约 5 秒后断开，不能由本次结果判断断连是否影响更长的动画。

另一种路径是控制程序连续发送颜色或亮度变化，让程序自己产生动画。当前临时试色约 1–2 秒后熄灭；连续发送的覆盖行为、速率和稳定性均未验证。Python demo 不以这条路径实现正式呼吸灯。

验证官方“单色呼吸”时，保持目标、RGB 和亮度与已成功请求相同，只把灯效编号从 `0` 改为 `1`。发送一条请求后，观察灯珠是否周期性变亮和变暗、周期时长、持续时长，以及 BLE 断开后是否继续。若设备只收到一条请求就持续产生周期变化，可确认动画在设备侧执行。测试前后都记录原始通知和实体表现。

## 程序结构

Python demo 与未来 Rust 程序使用同一组概念：

1. **目标层**：把用户输入的 `D1–D23` 转成协议点位 `0–22`。不向用户暴露 `24–39` 作为可控实体灯珠。
2. **报文层**：按命令生成完整字节序列，并拒绝不在允许范围内的字段。
3. **传输层**：识别设备，核对 `FFF0/FFF3/FFF4`，写入一条请求，保存每条原始通知。
4. **能力层**：只开放已完成相应验证的操作。实验性操作必须明确标注，并逐项收集实体观察。

当前 Python demo 的已验证基础范围是扫描、列表读取、全身及局部临时试色。实机还确认了全身预设的保存、详情读取和开启，但这些命令尚未纳入受限 CLI，等待断电恢复与删除闭环完成后再开放。临时局部 `33` 的后一条写入会覆盖前一条；多色布局不能通过连续临时试色表达。Rust 转写以 Python demo 的已验证行为和报文测试为输入。
