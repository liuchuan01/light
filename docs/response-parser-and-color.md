# APK 响应解析与调色盘代码核对

样本：`app-debug.apk`，SHA-256 `bf495209c45f08f636fcf783d52396f7fc5c93fdd07ff37ca84ec17cc1ceb820`。本页的解析规则来自 APK 静态代码；实机证据另见 [首次验证记录](device-test-2026-10-06.md)。字节偏移均从 0 开始，命令号与报文以十六进制表示。

## `FFF4` 通知进入解析器的路径

`ui.activity.LoginActivity` 的 `onCharacteristicChanged` 先取得本次通知的 `characteristic.getValue()`；只有特征对象等于保存的接收特征时，才把这次得到的 `byte[]` 直接交给 `BlueManagerUtil.handleRecData`。它还把相同字节打印成十六进制，并尝试按 GBK 转成文本用于日志；GBK 文本不参与协议解析。

`handleRecData` 的实际门槛是：长度 **大于 4**，且 `byte[0] == CC` **或** 最后一个字节等于 `55`。满足后，它把原始数组和 `byte[1]` 作为命令号交给所有监听器。这里没有同时验证包头包尾，也没有校验 `byte[2]`、`byte[3]`、校验和或长度字段。`DataManager` 的监听器按命令号启动协程，在协程中直接按数组偏移读取。

**当前主链路未见接收侧跨通知拼包或粘包拆包。** 每次 GATT 通知都独立进入上述路径；过短通知被丢弃，较长但不完整的通知可能通过门槛、随后在业务解析时越界。发送侧有按 `MAX_MTU` 分段写入的代码（初始 20 字节，MTU 协商成功后为 MTU 减 3，并在写入段之间等待约 20 ms），不能由此推断接收侧也会自动重组。下游应逐条保存原始通知和时间戳，不要先合并再覆盖原始记录。

## 列表响应 `40`、`30`、`50`

三条读取请求分别为 `BC 40 00 00 55`、`BC 30 00 00 55`、`BC 50 00 00 55`。`DataManager$onBlueDataListener$1$onBlueData$1.invokeSuspend` 对三个命令采用同一套偏移：

| 偏移 | APK 如何使用 | 当前能确定的含义 |
| --- | --- | --- |
| `0` | `handleRecData` 将其与 `CC` 比较；也可仅凭尾字节 `55` 放行 | 候选响应包头 |
| `1` | 作为分派命令号 | 对应 `40`、`30`、`50` |
| `2` | 列表解析器不读取 | 未知；不能直接命名为状态码 |
| `3` | Java `byte` 直接赋给 `int size` | APK 认为是列表项数量 `N`；这里未做无符号转换 |
| `4` 至 `3+N` | 循环读取并标记相应槽位 `isSet=true` | APK 认为是 `N` 个槽位索引；这里也未做无符号转换 |
| 末字节 | 只有在首字节不等于 `CC` 时才参与门槛判断 | 候选尾字节 `55`；业务解析器不检查其位置 |

`40`（全身）建立 4 个槽位，预期索引 `0..3`；`30`（局部预设）建立 14 个槽位，预期索引 `0..13`；`50`（高级）建立 4 个槽位，预期索引 `0..3`。这些上限是 App 数组大小，并非设备宣告的容量。**代码推导的完整候选帧**为 `CC cmd ? N slot[0] ... slot[N-1] 55`，长度 `5+N`；其中 `?` 的语义未知。APK 本身没有完整帧校验，故候选帧结构仍要由多条原始通知确认。

已录到的 `CC 40 00 00 55` 在 APK 中会走 `40` 分支，并因偏移 3 为 `00` 而按 `N=0` 处理，随后触发下一类列表查询 `30`。这只是“APK 会如何解释它”；单次实测不足以证明设备内部真的没有全身预设，或偏移 2 的 `00` 是成功状态。

当 `N>0`，App 会查询被标记的槽位详情：全身 `41`、局部 `31`、高级 `51`。对于已设置的高级槽位，App 还会查询自定义顺序 `52`。下游独立测试应保持现有约束：先记录并核对完整列表通知，再按已确认索引决定是否读详情。不要根据尾字节、通知总长度或灯珠数量猜测槽位索引。

### 对原始通知的核对方法

1. 每次请求单独保存 TX、所有 RX、时间戳和 GATT 特征 UUID，不丢弃不认识的通知。
2. 先检查本次 RX 是否满足 APK 的宽松门槛，再单独检查更严格的候选帧条件：`CC` 包头、`55` 包尾、命令匹配、`N` 不超过 App 槽位上限、实际长度等于 `5+N`、索引落在该类槽位范围且无重复。
3. 严格检查不通过时保留原始数据并标注原因；不要替 APK 或固件自动修正数量、拼接通知或把 `byte[2]` 定义为状态码。
4. 比较 `40`、`30`、`50` 的多次原始响应后，再决定能否把候选帧结构写成设备协议。

### 后续详情解析的代码线索（当前阶段不发送）

只有列表实测确认具体槽位后，以下偏移才可用于下一阶段。它们仍是 APK 对单次通知数组的访问方式，不是已验证的固件格式。

| 详情命令 | APK 读取的偏移 |
| --- | --- |
| `41` 全身详情 | `4`=槽位，`5`=是否选中，`6`=颜色类型，`7..9`=RGB，`10`=亮度，`11`=灯效编号，`12`=方向，`13`=速度。 |
| `31` 局部预设详情 | `4`=槽位，`5`=点位数量 `P`，`6..5+P`=点位索引；从数组末尾倒数第 7、6..4、3、2 字节分别读取颜色类型、RGB、亮度、灯效值。 |
| `51` 高级详情 | `4`=槽位，`5`=是否选中，`6`=局部预设数量 `P`，`7..6+P`=局部预设索引，`7+P`=模式，`8+P`=方向，`9+P`=速度。 |
| `52` 高级顺序 | `(array[3] & 0xFF)-1` 作为重复记录区的长度；从 `5` 起按“顺序位置、点位数量、点位索引列表”循环解析。 |

局部详情解析用数组总长度定位尾部字段，若通知只到达前半段，就可能把错误字节当成颜色；因此这部分尤其不能在没有原始完整帧证据时直接实现。

## 调色盘与 RGB 发包

App 确实有可交互的调色盘：`view.CircularColorPicker` 用色相环和径向白色渐变绘图，触摸时从渲染位图的触点读取 ARGB 颜色，并回调编辑页。`FullBodySettingActivity` 和 `PresetSettingActivity` 接收该颜色，依亮度滑块用 HSV 的 V 分量计算预览色，将结果存入 `color1`。`BlueCmdManager` 发送前用 `color & 0xFFFFFF` 去掉 Alpha，依次取 `R=(rgb>>16)&FF`、`G=(rgb>>8)&FF`、`B=rgb&FF`，作为连续三个字节写入试色或保存报文；亮度 `light` 另占一个字节。

因此代码没有“所有颜色”枚举表。RGB 字段理论上可表示 `256³ = 16,777,216` 种字节组合；触摸调色盘实际上能选到哪些组合受位图尺寸、插值和亮度变换影响，设备能显示多少颜色也尚未逐一验证。对下游的颜色试验，应固定已成功的 `43` 临时预览报文，只改变 `R/G/B` 三字节并记录视觉结果；如果要严格复现 App 在某个亮度滑块位置的取色，需考虑它先按 HSV 亮度缩放 RGB，再把亮度字节单独发送。编辑页虽有第二色块和“渐变色”选项，当前 `32/33/42/43` 组包只发送第一组 RGB，不能据此假设能通过这四条命令指定两个独立 RGB 颜色。
